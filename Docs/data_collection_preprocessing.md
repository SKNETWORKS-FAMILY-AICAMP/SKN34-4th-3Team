# 수집된 데이터 및 데이터 전처리 결과서

## 1. 개요

청년·1인 창업자 AI 행정·재정 지원 플랫폼이 사용하는 원천 데이터의 수집 현황과, 수집한 데이터를 DB 적재 및 LLM 학습(임베딩)에 사용 가능한 형태로 가공한 전처리 과정을 정리한다.

데이터는 크게 두 축으로 구성된다.

- **세법 자료**: 국가법령정보센터 API로 수집한 법령 전체 조문
- **지원정책·공고 데이터**: 정부24·K-Startup·기업마당·온통청년 4개 API로 수집한 정책·공고 정보

| 온통청년 | 여성가족부 | "일자리" 대분류 중 창업 또는 벤처·중소기업·대출·자금·보증 키워드 포함, "축제·장학금" 등 무관 키워드는 제외 | `policies` + `announcements` |

| --- | --- |
| 정책(`policies`) 총계 | **2,931건** |
| 공고(`announcements`) 총계 | **2,187건** |

정책과 공고의 건수가 다른 이유: `policies`는 정책 정보 자체를 담는 테이블이고, `announcements`는 그중 신청 마감일 등 구체적인 모집 정보가 확인되는 것만 별도로 담는 하위 테이블이다. 정부24처럼 공고 없이 정책 정보만 수집되는 소스가 있어 정책 수가 공고 수보다 많다.

같은 정책이 여러 소스에서 중복 수집되는 것을 막기 위해, 저장 전 정책 제목(`title`) 기준으로 기존 행을 조회하고 없을 때만 신규로 등록한다.

## 3. 데이터 전처리

### 3.1 DB 파트

#### 3.1.1 수집 기준 필터링

전처리 이전 단계로, 수집 시점에 관련 없는 데이터가 애초에 들어오지 않도록 소스별로 필터를 적용했다. (필터 조건은 [2.2](#22-지원정책공고-데이터) 표 참고)

#### 3.1.2 중복 데이터 제거

정책 제목(`title`) 또는 공고 원문 URL(`source_url`) 기준으로 DB에 이미 존재하는 행인지 확인한 뒤, 신규 데이터만 저장한다. 여러 소스에서 같은 정책·공고가 중복 수집되는 것을 방지한다.

#### 3.1.3 지역명 정규화

소스마다 지역 표기 방식이 달라("충청남도", "서울특별시", "전남광주통합특별시" 등) 이를 17개 시·도 단위의 통일된 짧은 이름("서울", "충남" 등)으로 변환했다.

처리 순서:
1. 매핑 테이블에서 정확히 일치하는 표기를 즉시 변환
2. 일치하지 않으면 첫 단어(공백 기준) 기준으로 재시도
3. 그래도 없으면 3글자 이상인 지역명이 문자열에 포함되어 있는지로 재시도
4. 고용노동부·중소벤처기업부 등 중앙부처처럼 지역 정보가 없는 경우 `NULL` 처리
5. 이미 적재된 기존 데이터도 동일 규칙으로 일괄 정규화(백필)

### 3.2 LLM 파트

정책·공고·세법 원천 데이터를 임베딩에 적합한 형태로 정제·청킹한 뒤 PostgreSQL `pgvector`(`rag_documents`)에 적재한다. 원천 DB(`policies`·`announcements`·`tax_documents`)는 수정하지 않고, 정제·임베딩 결과만 파생 테이블에 저장하는 구조다.

```text
DB 원천 조회 → 텍스트 노이즈 정제 → 의미 라벨을 붙여 검색용 본문 구성
→ 한국어 문장 경계를 고려한 청킹 → OpenAI 임베딩 생성 → rag_documents 적재
```

#### 3.2.1 특수문자 등 정제

정책과 세법 문서는 `clean_text()` 함수로 동일한 규칙을 적용한다. 검색 의미가 있는 숫자·단위·기호(나이, 비율, 금액, 법률 표현 등)는 유지하고, 크롤링·문서 서식에서 생긴 노이즈만 제거하는 것이 기준이다.

정제 순서:

1. `None`은 빈 값으로 처리
2. `&nbsp;`, `&amp;` 등 HTML 엔티티를 실제 문자로 변환
3. 잘못 디코딩된 대체 문자(`�`) 제거
4. 문자열로 들어온 `\r`, `\n`, `\t`를 공백으로 변환
5. HTML 주석·태그 제거
6. 원문자 번호(`①~⑳`)를 `1. ~ 20.` 형식으로 변환
7. 제어문자·보이지 않는 포맷 문자 제거
8. 연속된 공백·줄바꿈을 하나의 공백으로 결합
9. `○`, `●`, `■`, `▶`, `☞` 등 글머리표를 `-`로 통일
10. 반복된 `_`, `=`, `※` 서식 문자를 하나로 축소
11. `지 원 대 상`처럼 띄어진 항목명을 정상 표기로 결합
12. 연속된 하이픈 결합, 문장 앞 불필요한 하이픈 제거
13. 정제 후 내용이 없으면 `None`으로 처리

**정제 예시**

```text
정제 전: <p>청년&nbsp;지원</p>\u200b\x00  사업
정제 후: 청년 지원 사업

정제 전: ① 지원대상 ② 지원내용 ○ 신청방법 ● 제출서류
정제 후: 1. 지원대상 2. 지원내용 - 신청방법 - 제출서류
```

관련 코드: `LLM/src/data/postgres_repository.py`의 `clean_text()`

#### 3.2.2 검색용 본문 구성 (라벨링)

정제된 값은 필드명만 이어 붙이지 않고, 임베딩 모델이 의미를 구분할 수 있도록 한글 라벨을 붙여 하나의 본문으로 만든다. 값이 없는 필드는 본문에서 제외한다.

```text
[정책 문서 예시]
정책명: 청년전용창업자금
지역: 서울
분야: 고용·창업
지원대상: 대표자가 만 39세 이하인 자
지원내용: 시설자금 및 사업화 자금 지원
```

세법 문서는 `문서명 / 법령명 / 조문 내용`으로, 공고 문서는 `정책명 / 신청 시작일 / 신청 종료일 / 공고 내용`으로 구성한다. `100분의 75` 같은 법률 표현은 임의로 바꾸지 않고 원문 그대로 보존한다.

#### 3.2.3 청크 단위 분할

`RecursiveCharacterTextSplitter`로 분할하며, 현재 설정은 다음과 같다.

| 설정 | 값 | 의미 |
| --- | ---: | --- |
| `CHUNK_SIZE` | 1,000자 | 청크 하나의 최대 문자 수 |
| `CHUNK_OVERLAP` | 150자 | 인접 청크가 공유하는 문자 수 |

한국어 문맥을 최대한 보존하기 위해 아래 순서로 분할 경계를 찾는다.

```text
빈 줄 → 줄바꿈 → "다. " → "요. " → ". " → 공백 → 문자 단위
```

청크 ID는 원천 유형·원천 ID·청크 순번으로 만든다(예: `policy-101-chunk-1`). 세법 청크는 특정 정책에 속하지 않으므로 `policy_id`가 `NULL`이다.

관련 코드: `LLM/src/features/document_processing.py`, `LLM/src/features/indexing.py`

#### 3.2.4 임베딩 및 Vector DB 적재

정제·청킹이 끝난 본문을 OpenAI 임베딩 모델(`text-embedding-3-small`)로 벡터화해 `rag_documents.embedding`(pgvector)에 저장한다. 재색인 시에는 청크 본문의 SHA-256 해시를 비교해 **변경된 청크만** 다시 임베딩하여 불필요한 API 비용과 처리 시간을 줄인다(전체 강제 재임베딩은 `--force` 옵션으로 수행).

관련 코드: `LLM/src/vectorstores/postgres.py`
