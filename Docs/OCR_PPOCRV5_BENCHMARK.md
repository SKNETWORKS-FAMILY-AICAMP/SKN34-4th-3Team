# 영수증 OCR 엔진 교체: Tesseract → PP-OCRv5 한국어

> 작성일 2026-10-02 · 기준 브랜치 `feature_frontend`
> 대상 코드: `LLM/src/features/receipt_ocr.py`
> 요약: 영수증 OCR 기본 엔진을 PaddleOCR **PP-OCRv5 한국어**로 바꿨다. 같은 영수증 5장에서 Tesseract보다 **정확하고(34개 중 33개 vs 28개) 2배 빠르다(12.1초 vs 25.9초).** paddle을 쓸 수 없을 때는 기존 Tesseract 경로로 읽는다.

## 2. 테스트 방법

### 2.1 테스트 이미지

실제 사용자가 올린 영수증 5장. 사람이 이미지를 보고 정답 문자열을 미리 적어 두었다.

| 이름 | 종류 | 정답 항목 |
| --- | --- | --- |
| r10 | 카드 앱 캡처 (영문 가맹점 RUNPOD) | 상호 · 거래일 · 합계 |
| r14 | 간이영수증 이미지 (광화문한우마을) | 상호 · 거래일 · 합계 · 품목명 2개 |
| r17 | 카드 앱 캡처 (영문 가맹점 OPENAI) | 상호 · 거래일 · 합계 |
| r18 | 촬영 영수증, 90도 회전 | 거래일 · 합계 · 품목 금액 4개 · 품목명 4개 |
| r28 | 촬영 영수증, 90도 회전 | 거래일 · 합계 · 품목 금액 7개 · 품목명 4개 |

정답은 모두 34개다. 참고용으로 책 페이지 1장(r48, 정답 5개)도 따로 쟀다.

### 2.2 채점

- OCR 결과 글자에 정답 문자열이 들어 있으면 맞힌 것으로 센다.
- 비교 전에 공백, 쉼표, 마침표, 하이픈, 슬래시, 콜론을 지운다. 예: `2026.08.18`과 `2026-08-18`은 모두 `20260818`로 비교한다.

### 2.3 시간 측정

- 모델을 한 번 불러오고 예열 1회를 한 뒤 잰다. 서버에 모델을 띄워 두고 쓰는 실제 상황과 같다.
- 영수증마다 두 번 재서 빠른 쪽을 쓴다. 다른 컨테이너 부하로 흔들리는 값을 줄이기 위해서다.
- 환경: 개발 PC의 Docker(CPU 8코어). 다른 프로젝트 컨테이너(Backend, LLM, DB, Elasticsearch, Vite)가 함께 돌고 있었다.
- 패키지: Python 3.12 / 3.13, `paddlepaddle==3.2.2`, `paddleocr==3.7.0`.

## 3. 1차 비교: 어떤 엔진을 쓸까 (2026-10-01)

| 엔진 | 맞힌 수 (34개 중) | 상호 | 거래일 | 합계 | 품목 금액 | 품목명 | 책 페이지 | 5장 처리 시간 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Tesseract (기존 `run_ocr`: 전처리 3종 + 회전 재시도) | 28 (82%) | 3/3 | 5/5 | 5/5 | 10/11 | 5/10 | 3/5 | 25.9초 |
| PP-OCRv6 (기본 언어) | 23 (68%) | 2/3 | 5/5 | 5/5 | 11/11 | **0/10** | 0/5 | 51.7초 |
| **PP-OCRv5 한국어** | **33 (97%)** | 3/3 | 5/5 | 5/5 | 11/11 | 9/10 | 5/5 | 60.4초 |
| PaddleOCR-VL-1.6 (0.9B) | 결과 없음 | | | | | | | |

- **PP-OCRv6:** 한국어 모델이 아니어서 한글 품목명을 하나도 읽지 못했다.
- **PaddleOCR-VL-1.6:** 모델을 불러오는 단계까지만 진행됐고, 영수증 결과는 나오지 않았다.
- **PP-OCRv5 한국어:** 정확도가 가장 높았다. 다만 이때는 가장 무거운 설정이라 Tesseract보다 2.3배 느렸다. 그래서 2차로 속도를 줄이는 설정을 찾았다.

## 4. 2차 실험: PP-OCRv5 한국어 속도 줄이기 (2026-10-02)

### 4.1 하나씩 적용한 결과

| 설정 | 맞힌 수 | 5장 처리 시간 | 1차 설정 대비 |
| --- | --- | --- | --- |
| 1차 설정: 기본(server) 검출 모델, 글줄 방향 분류 켬, 긴 변 2000px | 33 | 51.2초 | 기준 |
| ① 검출 모델을 `PP-OCRv5_mobile_det`로 | 33 | 28.0초 | 1.8배 |
| ② + 글줄 방향 분류 끄기 (`use_textline_orientation=False`) | 33 | 22.5초 | 2.3배 |
| ③ + 검출 긴 변 1600px (`text_det_limit_side_len=1600`) | 33 | 16.7초 | 3.1배 |
| **④ + CPU 스레드 4개 (`cpu_threads=4`) ← 최종** | **33** | **12.1초** | **4.2배** |

최종 설정의 영수증별 처리 시간은 다음과 같다.
- 카드 앱 캡처: 1.3~1.8초
- 간이영수증: 0.3초
- 90도 회전 촬영 영수증: 4.0~4.8초

### 4.2 효과가 없거나 나빴던 시도

| 시도 | 결과 | 판단 |
| --- | --- | --- |
| 긴 변 1280px | 17.4초, 32/34 (품목명 1개 누락) | 빨라지지 않고 정확도만 떨어짐 |
| 긴 변 960px | 16.3초, 31/34 | 같은 이유로 제외 |
| server 검출 모델 + 글줄 방향 분류 끄기 | 48.9초 | 느린 원인은 검출 모델이었다 |
| 스크린샷(PNG)은 문서 방향 분류 생략 | 16.2초 (③과 같음) | 방향 분류 모델 자체가 가벼워 효과 없음 |
| CPU 스레드 2 / 6 / 8개 | 13.8 / 13.9 / 16.3초 | 4개가 가장 빠름. CPU를 다른 컨테이너와 나눠 쓰기 때문으로 보인다 |
| 고성능 추론 모드 (`enable_hpi=True`) | 12.3초 | 이득이 없고 추가 패키지 설치가 필요해 제외 |
| 글줄 묶음 크기 16 (`text_recognition_batch_size=16`) | 24.8초 | 오히려 느림 |
| CPU 가속 끄기 (`enable_mkldnn=False`) | 62.1초 | 기본값(켜짐)을 유지해야 한다 |

### 4.3 최종 설정

```python
PaddleOCR(
    text_detection_model_name="PP-OCRv5_mobile_det",
    text_recognition_model_name="korean_PP-OCRv5_mobile_rec",
    use_doc_orientation_classify=True,   # 90도 돌아간 사진 때문에 유지
    use_doc_unwarping=False,
    use_textline_orientation=False,
    text_det_limit_type="max",
    text_det_limit_side_len=1600,
    cpu_threads=4,                       # 환경변수 OCR_CPU_THREADS로 바꿀 수 있다
)
```

## 5. 서비스 적용 내용

### 5.1 동작 방식

1. `run_ocr()`가 PP-OCRv5로 읽는다. 다음 경우에는 기존 Tesseract 경로(`run_tesseract_ocr()`)로 대신 읽는다.
   - paddle을 불러오지 못한 경우(설치 누락, 모델 없음 등)
   - 실행 중 오류가 난 경우
2. 모델은 프로세스당 한 번만 만든다. 추론은 잠금(lock)으로 한 번에 하나씩 처리한다.
3. 서버가 첫 HTTP 요청(헬스체크 포함)을 받으면 백그라운드에서 모델을 미리 불러 둔다. 그래서 첫 영수증이 로딩 시간을 기다리지 않는다.
4. PP-OCR은 글자 덩어리를 따로따로 돌려준다(예: `베이컨토마토`, `5,480`, `1`). 세로 위치가 같은 것끼리 한 줄로 묶어야 LLM이 품목과 금액을 짝지을 수 있으므로 묶어서 넘긴다.
   - 결과 예: `청정원 베이컨 토마토 5,480 1 5,480`
   - 신뢰도는 0~1 값을 0~100으로 바꿔 기존과 같은 형식으로 넘긴다. 그래서 LLM 프롬프트와 `ocrConfidence`는 그대로 쓸 수 있다.

### 5.2 바뀐 파일

| 파일 | 내용 |
| --- | --- |
| `LLM/src/features/receipt_ocr.py` | 기본 엔진을 PP-OCRv5로 변경. Tesseract 경로는 `run_tesseract_ocr()`로 이름을 바꿔 대체 경로로 유지. `warm_up()`과 줄 묶기(`_group_rows`) 추가 |

## 7. 주의할 점

- **이미지 크기 증가:** LLM Docker 이미지가 1.57GB에서 4.83GB로 커졌다. paddle 패키지와 모델 때문이다. 배포 서버 디스크 용량을 확인해야 한다.
- **paddlepaddle 버전 고정:** 3.3.1은 CPU 추론에서 `NotImplementedError: ConvertPirAttribute2RuntimeAttribute not support ...`(oneDNN) 오류가 나서 3.2.2로 고정했다. 올릴 때는 영수증 OCR을 다시 확인해야 한다.
- **numpy 하향:** paddleocr 3.7.0이 numpy 2.4 미만을 요구해, 프로젝트 numpy를 2.5.2에서 2.3.5로 내렸다. LLM 코드에서 numpy는 OCR 모듈만 쓴다.
- **CPU 스레드 수:** 4개는 개발 PC 기준 최적값이다. 배포 서버에서는 `OCR_CPU_THREADS` 환경변수로 맞춘다.
- **동시 처리:** 추론을 한 번에 하나씩 처리하므로, 영수증 여러 장이 동시에 들어오면 순서대로 처리된다.
- **표본 크기:** 영수증 5장 기준 결과다. 다른 영수증(흐린 사진, 긴 영수증 등)으로 추가 확인하는 것이 좋다.
- **상호 인식:** r18처럼 상호가 로고로 인쇄된 영수증은 상호를 읽지 못한다(`vendor=None`). 엔진과 무관한 한계다.

## 8. 다시 측정하는 방법

측정 스크립트는 저장소에 넣지 않았다. 다시 잴 때는 아래 순서를 따른다.

1. `python:3.12-slim` 컨테이너에 다음을 설치한다.
   - 시스템 라이브러리: `libgl1`, `libglib2.0-0`, `libgomp1`
   - 패키지: `paddlepaddle==3.2.2`, `paddleocr==3.7.0`
   - 또는 새 LLM 이미지(`skn34-4th-3team-llm`)를 그대로 쓴다.
2. 설정마다 `PaddleOCR(...)`를 한 번 만들고 예열 1회를 한다. 그다음 영수증마다 `predict()`를 두 번 실행해 빠른 시간을 기록한다.
3. 결과 글자를 2.2의 채점 방식으로 정답 34개와 비교한다.
