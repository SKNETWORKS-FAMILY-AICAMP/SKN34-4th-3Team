# 세금 RAG Semantic Cache 응답 속도 개선 보고서

작성일: 2026-09-14

## 결론

세금 RAG는 정확도를 위해 Multi-hop 검색과 Hop별 근거 판정을 유지해야 한다. 이 구조에서는 첫 질문이 여전히 오래 걸리지만, PostgreSQL 기반 Semantic Cache를 적용한 뒤 반복되거나 의미가 같은 질문의 검색·근거 판정 단계를 재사용할 수 있게 됐다.

동일한 62턴 평가셋에서는 턴 통과율 **77.4%를 유지하면서 평균 응답 시간이 17.69초에서 12.46초로 5.23초(29.6%) 감소**했다. 실제 프론트 요청에서도 평균 처리 시간이 25.60초에서 19.89초로 줄었고, 30초 이상 장기 요청은 9건 중 4건에서 2건으로 감소했다. 통제된 유사 질문 비교에서는 26.0초가 11.2초로 줄어 판정 캐시의 직접적인 효과도 확인했다.

> **검색 품질을 낮추지 않고, 이미 검증한 검색 결과와 판정을 반복 사용해 지연을 줄이는 방식이 유효하다.**

평가 전 수치는 [정확도 우선 세금 평가](03_TAX_FINAL_RESULT.md), 캐시 적용 후 수치는 [캐시 Warm 상태 세금 평가](LLM_TAX_HALF_20260914_210435.md)를 사용했다. 두 평가 모두 같은 `holdout250` 세금 31개 시나리오·62턴을 대상으로 하며 통과 결과도 동일하다.

## 실제 프론트 사용 결과

LLM 컨테이너의 `TAX_LATENCY stage=total` 중 Backend를 통해 들어온 `/rag/chat` 요청만 집계했다. 개발자가 직접 호출한 검증 요청은 제외했다.

| 구간 | 요청 수 | 평균 | 중앙값 | 20초 미만 | 30초 이상 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 판정 서명 적용 전 관찰 구간 | 9건 | 25.60초 | 20.04초 | 4건 | 4건 |
| 판정 서명 적용 후 관찰 구간 | 9건 | **19.89초** | **18.29초** | **6건** | **2건** |

적용 후 9건의 처리 시간은 다음과 같다.

`38.13초 → 13.37초 → 18.29초 → 27.80초 → 33.55초 → 17.13초 → 6.26초 → 18.70초 → 5.77초`

캐시가 충분하지 않은 초기 요청에서는 30초대 응답이 남았지만, 질문이 누적된 뒤에는 같은 구간에서 6초 안팎의 응답이 확인됐다. 즉 장기 지연이 완전히 제거된 것은 아니지만, 질문이 반복될수록 빠른 응답의 비중이 증가하는 방향은 확인됐다.

이 비교는 실제 사용 흐름을 관찰한 운영성 표본이며 전후 질문 구성이 완전히 같지는 않다. 따라서 평균 22.3% 감소만으로 인과관계를 확정하지 않고, 아래 동일·유사 질문 실측과 함께 해석했다.

## 동일·유사 질문 통제 비교

| 검증 내용 | 첫 요청 | 캐시 재사용 요청 | 단축 효과 | 결과 일관성 |
| --- | ---: | ---: | ---: | --- |
| 문맥이 포함된 동일 후속 질문 | 51.39초 | 29.65초 | **21.74초, 42.3% 감소** | 검색 문서 재사용 후 판정 재실행 |
| 표현만 다른 청년창업 감면 질문 | 26.0초 | 11.2초 | **14.8초, 56.9% 감소** | 두 요청 모두 근거 부족 상태, 출처 포함 |

두 번째 비교에서는 대화 기록이 없는 새 요청이었지만 질문 유형과 핵심 조건이 같아 근거 판정 캐시가 사용됐다. 두 번째 요청 로그에는 근거 판정 LLM 단계가 나타나지 않았으며 응답 상태는 첫 요청과 동일했다. 단순히 문장을 그대로 저장하는 캐시보다 실제 서비스 질문 변형에 적합하다는 근거다.

## 평가셋 반복 실행에서 확인한 효과

캐시를 채운 첫 실행과 같은 평가셋을 바로 반복한 결과도 비교했다.

| 실행 | 턴 통과율 | 시나리오 통과율 | 평균 응답 시간 |
| --- | ---: | ---: | ---: |
| 캐시 초기 적재 실행 | 45/62, 72.6% | 18/31, 58.1% | 12.86초 |
| 동일 평가셋 Warm 실행 | **48/62, 77.4%** | **21/31, 67.7%** | **12.46초** |

평균은 0.40초(3.1%) 감소했다. 전체 평가에는 캐시 효과가 작은 계산 질문과 빠르게 종료되는 질문도 섞여 있어 장기 Multi-hop 질문에서 확인한 단축 효과가 전체 평균에서는 희석된다. 통과율 상승은 LLM 실행 변동도 영향을 줄 수 있으므로 캐시가 정확도를 높였다고 단정하지 않는다. 다만 **속도를 줄이면서 통과율이 하락하지 않았다는 점**은 확인할 수 있다.

## 적용 방식

### 1. 법령 문서 검색 캐시

의미가 유사한 세금 질문은 이전에 검색한 법령 청크를 재사용한다. 청년창업 세액감면처럼 표현이 자주 달라지는 질문은 검색용 표준 주제로 정규화한다.

- 검색 유사도 기준: `0.92`
- 사용자 조건이 조금 달라도 공통 법령 문서는 재사용
- 이전 검색의 신규 청크만 저장해 Hop별 문서가 섞이지 않게 처리
- 저장된 문서가 변경되거나 사라지면 캐시를 사용하지 않음

### 2. 근거 판정 캐시

근거 판정은 문장 전체나 사용자 ID를 기준으로 저장하지 않는다. 다음 값으로 판정 서명을 구성한다.

- 표준 세금 질문 유형과 세부 목적
- 나이, 지역, 업종, 사업자 유형, 창업일
- 질문에 명시된 중요한 수치와 창업 조건
- 이전 Hop과 현재 Hop에서 확보한 근거 ID
- 사용한 LLM 모델과 판정 캐시 버전

표현과 대화방이 달라도 이 값들이 같으면 판정을 재사용한다. 반대로 나이·지역·업종·창업일 또는 근거가 달라지면 판정 LLM을 다시 실행한다. 근거 부족 판정은 법령과 상황 변화에 오래 고정되지 않도록 6시간만 유지한다.

### 3. PostgreSQL 영속 저장

캐시는 프로세스 메모리가 아니라 PostgreSQL의 `tax_rag_cache` 테이블에 저장된다. LLM 서버를 재시작해도 유지되며, 판정 서명을 기존 기본키로 사용해 캐시가 늘어나도 전체 JSONB를 순차 검색하지 않는다. `tax_rag_cache` 테이블은 `DB/app_extras.sql`에 추가했고 API 계약은 변경하지 않았다.

#### 테이블 생성

새 DB 볼륨은 `docker-compose.yml`의 initdb(`02_app_extras.sql`)에서 자동으로 생성한다. 이미 초기화된 볼륨은 initdb가 다시 실행되지 않으므로 한 번 직접 적용한다. `app_extras.sql`의 모든 구문은 재실행해도 안전하다.

```bash
docker exec -i startup_db psql -U $POSTGRES_USER -d $POSTGRES_DB < DB/app_extras.sql
```

#### 캐시 데이터를 다른 환경으로 옮기지 않는 이유

캐시는 법령 원문이 아니라 근거 청크의 `rag_documents.id` 목록과 저장 시각만 보관한다. 조회 시 현재 DB에서 원문을 다시 읽으며, `rag_documents.updated_at`이 캐시 저장 시각보다 늦으면 오래된 근거로 보고 사용하지 않는다. 따라서 한 DB에서 덤프한 캐시 데이터는 다른 환경에서 복원되지 않는다. 캐시 데이터 덤프는 저장소에 올리지 않고, 환경마다 빈 테이블에서 새로 채운다.

#### 캐시 선채움

첫 사용자 질문부터 캐시 효과가 필요한 환경은 데이터 적재와 LLM 서버 기동 후 기존 평가 러너로 캐시를 채운다. 러너가 실제 서버 graph를 호출하므로 해당 환경의 문서 ID, 저장 시각, `LLM_MODEL` 기준으로 캐시가 저장된다.

```bash
cd LLM
uv run python -m src.evaluation.run_evaluation --mode graph \
  --base-url http://localhost:8001 \
  --output evaluation/results/cache_warmup.json
```

- `--output`을 별도로 지정해 기존 평가 결과 파일을 덮어쓰지 않는다.
- `LLM_MODEL`을 변경하면 근거 판정 캐시는 사용하지 않고 법령 문서 검색 캐시만 재사용한다.

## 첫 질문이 느린 이유와 누적 효과

캐시에 없는 첫 질문은 기존과 동일하게 다음 작업을 수행한다.

`의도 분류 → Multi-hop 검색·Rerank → 근거 충분성 판정 → 최종 답변 생성 → 캐시 저장`

유사 질문이 다시 들어오면 다음과 같이 단축된다.

`의도 분류 → 문서·판정 캐시 검증 → 최종 답변 생성`

따라서 서비스 초기에는 첫 질문 비용이 남는다. 사용자가 늘고 세금 질문 유형이 반복되면 공통 법령 검색과 판정 결과가 누적되어 캐시 적중 범위가 넓어진다. 다만 모든 질문이 고유하거나 사용자 조건이 계속 달라지는 경우에는 적중률이 낮을 수 있으므로, 사용자 수 증가가 응답 시간 감소를 무조건 보장하는 것은 아니다.

## 정확도 보호 장치

이번 개선은 빠른 응답을 위해 기존 검색 단계를 제거한 방식이 아니다.

- Multi-hop, Dense, BM25, RRF, Cohere Rerank 유지
- 캐시 미적중 시 기존 전체 경로 수행
- 사용자 핵심 조건이 다르면 판정 재사용 금지
- 이전·현재 근거 ID가 다르면 판정 재사용 금지
- 법령 문서 변경 시 기존 캐시 무효화
- 관련 근거가 없을 때 기존 안전 응답 유지

관련 집중 테스트는 **17건 모두 통과**했으며, 서버 재시작 후 RAG 인덱스 `ready`, 문서 10,892개·청크 12,613개 상태에서 실측했다.

## 최종 판단

Semantic Cache는 세금 RAG의 가장 큰 병목인 반복 검색과 근거 판정 LLM 호출을 줄이면서 기존 정확도 우선 구조를 유지한다. 동일 평가셋에서 77.4% 통과율을 유지한 채 평균 응답 시간을 29.6% 줄였고, 실제 프론트 관찰에서도 평균 22.3% 감소와 30초 이상 요청 비중의 절반 감소를 확인했다.

첫 요청 지연은 남아 있지만 이후 동일·유사 질문은 5~11초대까지 단축됐다. 서비스 질문이 누적될수록 재사용 가능한 질문 유형이 늘어나는 구조이므로, 현재 요구사항인 **정확도 유지와 반복 요청 속도 개선을 함께 만족하는 방법**으로 판단한다.
