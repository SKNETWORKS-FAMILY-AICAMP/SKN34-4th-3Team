# 정책·세금 RAG 성능 개선 종합 보고서 — 2026-09-13

## 최종 결론

최초 250건 평가에서 확인된 핵심 문제는 **정책 검색의 낮은 재현율**과 **세금 법령 근거 답변의 낮은 통과율**이었다. 정책은 검색 경로와 개인화 검색을 보완해 목표 70%를 넘겼고, 세금은 법령 탐색을 보강해 최고 77.4%까지 올렸다.

속도 최적화 과정에서는 세금 근거 충분성 판정 LLM을 줄이면 평균 응답이 약 5초 빨라졌지만 통과율이 10%p 이상 하락했다. 세금·법령 답변은 잘못된 답변의 비용이 크므로 **속도보다 정확도를 우선하는 설정으로 최종 확정**했다. 긴 대기 시간은 검색 품질을 낮추는 대신 Frontend에서 5초 간격으로 진행 상태를 보여 주는 방식으로 보완했다.

정책의 최종 수치는 동일 평가셋을 반복 실행했을 때 관찰된 범위다. 세금 77.4%는 최종 채택 설정의 기준이 된 실측값이며, 근거 판정 축소 실험을 철회한 현재 코드에 대한 전체 재평가는 아직 다시 실행하지 않았다. 세금 단위 테스트 43건은 통과했다.

## 1. 최초 250건 평가에서 드러난 문제

[최초 250건 평가](01_EVAL_BASELINE.md)에서 Guardrail과 로드맵은 이미 유지 가능한 수준이었다. 개선 자원을 정책 검색과 세금 법령 근거에 집중할 수 있었다.

- 정책 검색 R@5는 64.3%로 목표 70%에 미달했다. 짧고 조건이 직접 드러난 질문보다 일반 문장, 노이즈가 섞인 질문, 사용자 프로필을 암묵적으로 사용해야 하는 질문에서 성능이 낮았다.
- 세금 전체 통과율은 66.1%였지만 법적 근거 유형은 4/18턴에 불과했다. Hop 수 자체보다 검색 결과에 필요한 조문이 없거나 근거 충분성 판정이 보수적으로 끝나는 것이 주된 문제였다.
- Guardrail은 63/63을 정확히 차단했고 정상 정책 질문 오차단도 없었다.
- 로드맵은 91.9%로 목표를 통과했다.

따라서 전체 Graph를 크게 바꾸는 대신 정책 후보 검색과 세금 법령 탐색을 별도로 보완하는 방향을 선택했다.

## 2. 단순 경로 분리만으로는 개선되지 않았다

로직 V2 재평가에서는 정책·세금 문서 경로를 분리하고 중복 제거와 기본값 처리를 보완했다. 그러나 정책 R@5는 63.5%, 세금 통과율은 62.9%로 오히려 소폭 낮아졌다.

이 결과로 다음 원칙을 정했다.

- Multi-hop의 Hop 수를 단순히 늘리지 않는다.
- Dense, BM25, RRF, Cohere Rerank 중 어느 단계에서 정답이 빠지는지 구분한다.
- 정책은 사용자 조건이 검색어에 실제로 반영되는지 확인한다.
- 세금은 법령명·조·항 등 명시적 참조를 다음 검색에 활용한다.
- Guardrail과 로드맵은 안정 영역이므로 불필요하게 수정하지 않는다.

## 3. 정책·세금 검색 정확도를 먼저 확보했다

[정책·세금 125건 재평가](02_ACCURACY_IMPROVEMENT.md)에서는 최초 250건 중 개선 대상인 정책 63문항과 세금 62턴만 같은 평가 기준으로 다시 실행했다.

정책에는 개인화 검색어 보강, 정책 ID 기준 중복 제거, Router 분기 수정, 검색 단계별 후보 점검을 반영했다. 그 결과 R@5가 63.5%에서 74.6%로 11.1%p 상승했고 정답을 전부 놓친 문항은 17건에서 10건으로 줄었다. 특히 프로필을 암묵적으로 사용해야 하는 질문이 51.6%에서 72.6%로 개선됐다.

세금에는 법령 문서 전용 검색, 명시적 조문 참조에 대한 후속 검색, 누적 근거 재사용, 법적 근거가 부족할 때만 추가 Hop을 수행하는 흐름을 보강했다. 세금 통과율은 62.9%에서 72.6%로 9.7%p 상승했다. 가장 취약했던 법적 근거 유형도 22.2%에서 55.6%로 개선됐다.

이 단계에서 정책과 세금 모두 목표 70%를 넘겼다. 이후 작업의 우선순위를 정확도 보완에서 응답 속도 개선으로 전환했다.

## 4. 추론 강도 조정은 작지만 안전한 개선이었다

추론 강도 비교에서 모델의 추론 강도를 `medium`에서 `low`로 낮췄다.

- 정책 대표 질문은 15.28초에서 10.19초로 33.3% 단축됐다.
- 세금 4건 평균은 15.95초에서 14.55초로 8.8% 단축됐다.
- 세금 4건의 자동 채점 결과는 변경 전후 동일했다.

정책과 세금의 Router·의도 분류·답변 생성 등 빠른 판단이 가능한 호출에 `low`를 적용했다. 다만 세금은 Multi-hop과 근거 판정 호출이 남아 있어 모델 설정만으로 큰 폭의 개선을 얻지는 못했다.

전체 반복 평가에서는 외부 모델 응답 변동이 컸다. 정책 R@5는 70%대, 세금 통과율은 69~76% 범위에서 움직였다. Docker 이미지를 다시 만들지 않은 실행도 섞였기 때문에 가장 높거나 가장 빠른 단일 결과를 그대로 최종값으로 채택하지 않고, 적용 상태와 외부 연동이 확인된 실행만 판단에 사용했다.

## 5. 세금 검색과 최종 Context를 최적화했다

세금 Multi-hop은 여러 법령과 조문을 함께 찾아야 하므로 제거하지 않았다. 대신 독립적인 1차 검색과 최종 답변 입력을 정리했다.

### 1차 검색 병렬화

대상 요건, 감면율, 지역 조건, 적용 기간처럼 첫 질문에서 바로 만들 수 있는 검색어는 동시에 조회하도록 변경했다. 각 검색은 기존 Dense·BM25·RRF 결과를 사용하며, 결과를 합친 뒤 기존 Rerank를 수행한다. 이전 검색 결과에 따라 법령이나 검색어가 결정되는 후속 Hop은 순차 구조를 유지했다.

### 누적 근거와 Context 정리

검색 Recall을 낮추는 임의의 top-k 축소는 하지 않았다. 검색이 끝난 뒤 최종 LLM에 전달하기 직전에 같은 문서·법령·조항과 내용이 크게 겹치는 청크를 정리했다. 중복 출처 번호는 유지해 인용 관계가 깨지지 않게 했고 서로 다른 법령과 조항은 보존했다.

최종 답변은 결론, 적용 조건, 필요한 계산 결과, 근거 법령과 핵심 이유, 주의사항 중심으로 간결하게 생성하도록 조정했다. 같은 설명 반복과 긴 법령 원문 인용은 줄였다.

### 시간 제한과 관측성

각 세금 검색 Hop의 검색·Rerank 구간에는 최대 20초 제한을 두었다. Rerank가 시간 안에 끝나지 않으면 기존 RRF 결과를 사용한다. 이 제한은 검색 Hop에만 적용되므로 전체 답변 시간이 20초로 제한되는 것은 아니다.

다음 단계의 시간을 로그로 남기도록 했다.

- 세금 의도 분류
- 계산 계획
- 검색과 Rerank
- 근거 충분성 판정
- 다음 Hop 검색어 생성
- 최종 답변 생성
- 전체 처리 시간

프로파일링한 대표 장기 지연 요청에서는 세금 Graph 32.32초 중 근거 충분성 판정 LLM 2회가 20.73초를 차지했다. 검색·Rerank는 4.36초, 의도 분류는 3.02초, 최종 생성은 4.17초였다. 병목은 검색 자체보다 **근거 판정 LLM의 긴 꼬리 지연**에 있었다.

## 6. 빠르게 보였지만 제외한 잘못된 평가

속도 실험 중 두 결과는 정상 처리시간으로 사용하지 않았다.

| 실행 | 표시된 결과 | 문제 | 판단 |
| --- | ---: | --- | --- |
| Cohere 사용 제한 발생 | 58.1%, 7.81초 | Rerank 호출 실패 후 품질이 급락 | 속도 개선 근거에서 제외 |
| Docker 재생성 후 재색인 누락 | 58.1%, 9.61초 | 인덱스가 `not_ready`, 문서·청크 0개, 다수 요청 조기 종료 | 평가 전체 무효 |

Cohere 키 변경 후 실제 Rerank 연결을 확인했고, Docker 재생성 뒤에는 RAG 상태가 `ready`이며 문서 10,892개·청크 12,613개가 연결됐는지 확인한 후 평가했다. 이 과정을 통해 **비정상 조기 종료는 평균 응답 시간을 크게 낮춰 보이게 한다**는 점을 확인했다.

## 7. 근거 판정 LLM 축소 실험과 최종 선택

가장 큰 병목이 근거 충분성 판정 LLM이었기 때문에 중간 Hop에서는 규칙으로 명시적 법령 참조를 따라가고, 누적 근거의 마지막 단계에서만 LLM을 호출하는 방식을 실험했다.

| 세금 설정 | 턴 통과율 | 시나리오 통과율 | 평균 응답 시간 | 결정 |
| --- | ---: | ---: | ---: | --- |
| 정확도 우선 기준 | **77.4%** | **67.7%** | 17.69초 | 최종 채택 |
| 중간 판정 축소 | 66.1% | 54.8% | 12.84초 | 품질 하락으로 기각 |
| 모호한 경우 한 번 추가 판정 | 64.5% | 54.8% | **11.84초** | 품질 회복 실패로 기각 |

중간 판정 축소는 약 5초를 줄였지만 통과율이 11.3%p 하락했다. 모호한 사례에만 판정을 한 번 추가하는 절충안도 유의미한 품질 회복을 만들지 못했다. 세금 답변에서는 잘못된 법적 근거를 빠르게 제공하는 것보다 근거를 더 확인하는 것이 중요하다고 판단했다.

따라서 다음을 최종 확정했다.

- 세금 Multi-hop 유지
- 각 Hop의 근거 충분성 LLM 판정 유지
- 각 Hop의 기존 Rerank 유지
- 독립적인 1차 검색 병렬화 유지
- 검색 결과 누적·중복 제거와 간결한 최종 Context 유지
- 검색 Hop 20초 제한과 단계별 latency 로그 유지
- 정책 경로의 개선된 검색·Router 로직 유지

## 8. 사용자가 느끼는 대기 시간 보완

정확도 우선 설정에서는 세금 답변이 평균 17초대로 걸린다. 최종 답변은 검색과 근거 판정이 끝나야 확정되므로 현재 Graph 구조에서 답변 본문을 일찍 스트리밍하면 근거가 바뀌거나 최종 상태와 충돌할 수 있다.

대신 Frontend에서 요청 직후부터 진행 상태를 표시하고 5초마다 문구를 갱신하도록 했다. 진행 상태는 챗봇의 별도 메시지로 저장되지 않으며 답변 대기 영역에서만 보인다. 최종 답변이 도착하면 진행 표시는 제거되고 확정 답변과 근거가 표시된다.

## 최종 상태

정책은 최초 64.3%에서 70% 이상으로 개선해 목표를 달성했다. 세금은 최초 66.1%에서 최고 77.4%까지 개선했다. 세금 속도를 12초대로 낮추는 실험은 정확도를 크게 희생했기 때문에 채택하지 않았다.

최종 제품 방향은 다음과 같다.

> **정책 검색은 개선된 검색 성능을 유지하고, 세금 법령 답변은 정확도를 우선한다. 사용자가 기다리는 동안에는 진행 상태를 보여 줘 체감 지연을 줄인다.**

## 결과 해석 시 주의점

- 같은 `holdout250` 문항을 개선 과정에서 반복 사용했으므로 전후 회귀 비교에는 적합하지만 새로운 질문에 대한 독립적인 일반화 성능을 증명하지는 않는다.
- 정책 R@5와 세금 턴 통과율은 서로 다른 지표이므로 합산하지 않는다.
- 세금 자동 채점은 route, status, 차단 여부, 근거 유무 등을 검사한다. 77.4%가 법률 해석이나 계산 금액의 실제 정확도를 직접 의미하지는 않는다.
- 외부 LLM과 Cohere 응답 시간에는 실행별 변동이 있다. 평균 한 번만으로 작은 속도 차이를 확정하지 않는다.
- 최종 복원 코드의 수치 재확인이 필요하면 RAG 인덱스 `ready`와 Cohere 정상 연결을 먼저 확인한 뒤 세금 62턴을 한 번 더 실행해야 한다.
