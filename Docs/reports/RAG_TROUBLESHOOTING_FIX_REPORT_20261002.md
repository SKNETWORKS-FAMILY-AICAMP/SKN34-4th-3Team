# RAG 트러블 이슈 해결 보고서

작성일: 2026-10-02 · 대상: `feature/server` 작업 트리 · 상태: 로컬 수정·검증 완료

**기존 테스트 실패 6건을 해결하고, 검색·재색인·캐시의 추가 위험 경로를 보완했다. 최종 LLM 전체 테스트는 509개 통과, 실패 0건이다.**

점검 대상 검색 구성은 **PostgreSQL Dense + 메모리 BM25**다.

## 1. 무엇이 달라졌나

| 문제 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 기존 테스트 실패 | 전체 테스트 중 6건 실패 | 변경된 동작에 맞춰 갱신, 전체 통과 |
| Router 검색어 누락 | 검색어가 없으면 채팅이 HTTP 502로 실패 | 문맥이 복원된 원 질문으로 검색 |
| 준비 상태 오표시 | Dense만 준비돼도 `ready`, 첫 채팅에서 BM25 생성 실패 가능 | PostgreSQL Dense와 메모리 BM25가 모두 준비돼야 `ready` |
| 재색인 중간 실패 | 이전 BM25·그래프가 남고 `ready=True` 유지 가능 | 검색 상태 무효화, 새 검색 요청 차단, 재시도 성공 후 복구 |
| 세금 재정렬 후보 과다 | 검색어 5개 × 후보 20개 = 최대 100개 전달 사례 재현 | 결과를 다시 결합해 최종 후보를 설정값 이내로 제한, 기본 20개 |
| BM25 세금 근거 캐시 누락 | 청크 ID가 없는 근거가 포함되면 캐시 저장 생략 | 원본 문서 ID와 내용 해시로 저장·복원 |

### 실제 실패와 위험 재현의 구분

- **실제로 확인한 실패:** 로컬 테스트 6건 실패.
- **테스트로 재현한 위험:** Router 출력 누락, BM25 준비 실패, 재색인 중간 실패, 후보 수 초과, BM25 근거 캐시 저장 누락.
- 위 위험 경로가 실제 운영 장애로 발생했다는 로그는 이번 작업에서 확인하지 않았다. Router가 검색어를 자주 누락한다는 의미도 아니다.
- Cohere API 키·429 문제는 이번 수정 범위에서 제외했다.

## 2. 문제별 원인과 해결

### ① 기존 테스트 6건 실패

검색어 작성 책임이 Router로 이동하고, 운영 키워드 검색이 Elasticsearch에서 기본 BM25로 바뀌었지만 일부 테스트는 이전 동작을 기대하고 있었다.

| 실패 건수 | 원인 | 조치 |
| --- | --- | --- |
| 정책·세금 검색 3건 | 이전 문자열 정규화 결과를 기대 | Router 검색어를 그대로 사용하는 계약에 맞춰 기대값·fixture 갱신 |
| 재색인 API 2건 | 제거된 Elasticsearch 동기화 함수를 mock | 원본 문서 로딩과 메모리 BM25 준비·갱신을 검증하도록 변경 |
| 세금 캐시 1건 | 새 원본 문서 로더를 mock하지 않아 실제 DB 연결 시도 | DB 의존성을 mock하고 캐시에 PostgreSQL 검색기가 전달되는지 검증 |

공통 Fake 모델이 누락된 검색어를 자동으로 채우던 보정도 제거했다. 이제 테스트에서 실제 코드의 fallback을 확인한다.

### ② Router 검색어가 비어 있으면 채팅 전체 실패

**원인:** `search_query`가 누락·null·빈 문자열·공백이면 검증 단계에서 예외가 발생했다. 검색 단계에도 원 질문으로 대체하는 처리가 없었다.

**해결:** 정상적인 Router 검색어를 우선 사용하고, 비어 있을 때만 `_effective_query`로 대체한다. 대화 문맥이 복원됐다면 복원된 질문을, 그렇지 않다면 원 질문을 사용한다. 대체가 발생한 경우에는 로그를 남긴다.

**검증:** 정책·세금·공고 경로에서 각 빈 값의 채팅 처리와 문맥 복원 질문 사용을 확인했다. `out_of_scope`는 검색어 필드가 누락돼도 범위 밖 처리를 유지한다.

### ③ `ready`인데 첫 검색에서 실패

**원인:** 준비 상태는 Dense 인덱스 존재만 확인했다. 메모리 BM25는 첫 그래프 생성 시 DB에서 원본 문서를 읽어 만들었기 때문에, `ready` 이후에도 준비 실패가 발생할 수 있었다.

**해결:** PostgreSQL 인덱스 준비·재색인 과정에서 BM25까지 구성한다. 두 검색기가 준비돼야 `index_ready=True`를 반환한다.

**검증:** BM25 준비 전에는 `not_ready`, 준비 후에는 `ready`가 되는 것을 확인했다. 원본 문서 로딩 실패 시 성공 응답을 반환하지 않는다.

### ④ 재색인 중간 실패 후 이전 검색기 사용

**원인:** PostgreSQL 일부 갱신 후 원본 동기화가 실패하면 검색기 교체까지 도달하지 못했다. 이전 BM25·그래프가 남아 서로 다른 시점의 데이터를 검색할 수 있었다.

**해결:** PostgreSQL 재색인을 시작할 때 검색 상태를 무효화한다. 실패하면 무효화 상태를 유지하고, 새 검색 요청은 HTTP 409의 `RAG_INDEX_NOT_READY`로 반환한다. 재시도가 성공하면 새 검색기를 사용한다.

```text
재색인 시작 → 새 검색 요청 차단 → Dense 갱신 → BM25 준비 → ready 복구
                                      실패 → not_ready 유지 → 재시도
```

**검증:** 부분 갱신 이후 동기화 실패, BM25 로딩 실패, 실패 후 채팅 차단, 재시도 성공 후 복구를 확인했다.

이 조치는 무효화 이후 새로 시작하는 검색 요청에 적용된다. 이미 실행 중인 요청을 취소하는 기능을 추가한 것은 아니다.

### ⑤ 세금 재정렬 후보 20개 제한 초과

**원인:** 첫 검색에서 여러 검색어의 후보를 단순히 합쳤다. 검색어별로 20개 제한이 있어도 합친 결과는 100개까지 늘어날 수 있었다.

**해결:** 운영 세금 검색에서는 검색어별 Dense·BM25 순위를 모아 원본 문서 단위로 RRF를 다시 수행한다. 정확 조문 근거를 우선 포함한 뒤, 최종 재정렬 입력을 `cohere_rerank_candidate_k` 이내로 제한한다. 기본값은 20개다. 세금 근거 API에도 같은 최종 제한을 적용했다.

**검증:** 5개 검색어에서 서로 다른 후보 100개를 제공한 경우에도 재정렬 입력은 20개였다. 뒤쪽 검색어의 우수 후보가 반영되고, 정확 조문 근거도 제한 안에서 유지되는 것을 확인했다.

### ⑥ BM25 세금 근거가 캐시에 저장되지 않음

**원인:** 기존 캐시는 모든 근거에 `rag_documents.id`가 있어야 저장했다. BM25 원본 문서에는 해당 청크 ID가 없어서, 답변이 성공해도 캐시 저장을 건너뛰었다.

**해결:** 근거 종류에 맞춰 식별·복원한다.

| 근거 종류 | 캐시에 저장하는 식별 정보 | 복원·유효성 확인 |
| --- | --- | --- |
| Dense 청크 | 기존 `rag_documents.id` | 기존 청크 복원과 갱신 시각 검사 유지 |
| BM25 원본 문서 | 원본 문서 ID + 제목·출처·본문 해시 | 원본 전체 본문을 다시 읽고 해시 비교 |

BM25 문서 ID를 청크 ID로 대신 사용하지 않는다. 복원할 때 근거 순서와 전체 본문을 보존하며, 원본이 바뀌거나 삭제되면 해당 캐시를 재사용하지 않는다. 기존 정수 ID 기반 캐시도 계속 지원한다. DB 스키마 변경은 없다.

**검증:** BM25만으로 찾은 근거의 저장·캐시 HIT, Dense와 BM25가 섞인 근거의 순서·판정 복원, 본문·제목·출처 변경 및 삭제 시 캐시 무효화를 확인했다.

## 3. 최종 검증 결과

| 시점 | LLM 전체 테스트 결과 |
| --- | --- |
| 수정 전 | 458개 통과 / 6개 실패 |
| 1차 수정 후 | 501개 통과 / 실패 0건 |
| 추가 위험 보완 후 | **509개 통과 / 실패 0건** |

검색·재색인·캐시의 회귀 시나리오를 추가하면서 전체 테스트 수가 증가했다.

실행 명령: `LLM` 디렉터리에서 아래 명령을 사용했다.

```powershell
.\.venv\Scripts\python.exe -m pytest -q --tb=short -p no:cacheprovider
```

`git diff --check`도 통과했다. 위 결과는 외부 API와 실제 DB를 mock한 로컬 검증이며, 운영 DB·실제 LLM/Cohere API 연동 검증과 배포는 수행하지 않았다. 검색 품질이나 운영 응답 시간이 개선됐다는 실측 결과로 해석하면 안 된다.
