# 사업계획서 작업 흐름 정리 보고서

작성일: 2026-09-24

기준: 이번 사업계획서 관련 세션의 사용자 요청, 첨부 요구사항, 현재 Frontend·Backend·LLM 코드

## 1. 결론

현재 목표는 **사용자가 제공한 사실을 선택한 양식의 실제 입력 칸에 맞춰 작성하고, 부족한 정보는 먼저 사용자에게 묻는 흐름**이다. 공고와 양식은 모두 선택 사항이다. 양식이 있으면 해당 양식의 입력 칸을 기준으로, 없으면 기본 PSST 양식의 13개 항목을 기준으로 초안을 만든다. 초안은 평가 후 같은 화면에서 항목별로 수정하고, 수정 내용을 반영해 다시 생성·평가한 다음 다운로드한다.

이 보고서는 2026-09-23 인수인계 문서의 당시 화면 구성보다 이후 세션에서 확정된 흐름을 우선한다. 특히 별도 문서 미리보기 메뉴와 항목별 편집 페이지는 현재 흐름에 없다.

## 2. 세션에서 확정된 사용자 흐름

| 순서 | 화면 | 사용자 작업과 다음 동작 |
| --- | --- | --- |
| 1 | 계획 정리 | 기초 정보 6개와 아이디어 7개 항목을 작성하고 AI 정리 결과를 검토·수정한다. 추가 설명만 선택 입력이다. 개발 환경에는 소상공인 재고 관리 서비스 테스트 프리셋이 있다. |
| 2 | 공고 양식 선택 | 공고는 기본적으로 선택하지 않는다. 선택할 경우 저장 공고를 앞에 두고 관련 공고를 검색·스크롤해 카드에서 고른다. PDF/HWPX 양식도 선택 사항이다. |
| 3 | 양식 분석 | 양식이 있으면 파일의 작성 가능 위치를 추출하고 각 입력 칸의 목적, 필요한 정보, 기존 정보와의 연결, 부족한 정보를 분석한다. 별도 메뉴 단계가 아니라 초안 준비 과정에서 실행한다. |
| 4 | 계획 보완 | 양식 분석 결과 정보가 부족한 칸만 보여준다. 답변, `정보 없음`, `해당 사항 없음`, 이미지 첨부를 구분한다. 항목이 많으면 페이지로 나누며 입력값을 유지한다. 양식이 없거나 보완할 칸이 없으면 이 단계를 건너뛴다. |
| 5 | 초안 평가 | 초안 생성 직후 AI 평가를 실행하고 종합 점수·총평과 항목별 강점·보완점을 보여준다. 이 화면은 평가 확인용이며 문서 미리보기를 제공하지 않는다. |
| 6 | 초안 수정 | 현재 화면에서 항목별 텍스트나 표 셀을 수정한다. 제목에 마우스를 올리거나 키보드로 선택하면 해당 항목 평가를 볼 수 있다. 수정 후 내용을 바탕으로 초안을 다시 생성한다. |
| 7 | 재평가 및 저장 | 수정된 초안을 재평가해 점수와 간단한 총평을 보고 Markdown/PDF/HWPX 중 해당 양식에서 가능한 형식으로 다운로드한다. |

초안 생성·양식 분석·수정 반영 중에는 별도 로딩 대화상자를 표시한다. 사용자가 제거를 요청한 문서 미리보기와 별도 항목 편집 페이지로 되돌아가는 흐름은 적용하지 않는다.

## 3. 양식과 내용 작성 원칙

1. **공고와 양식은 독립적인 선택 사항이다.** 공고가 있으면 공고 기준을 평가에 반영한다. 공고가 없고 양식이 있으면 양식 기준으로, 둘 다 없으면 기본 PSST 양식 기준으로 작성·평가한다.
2. **양식은 섹션 제목만이 아니라 입력 칸 단위로 해석한다.** 글, 여러 줄, 목록, 표, 이미지, 인적 사항, 비입력 영역을 구분한다. 본문과 바로 아래 표, 같은 대분류의 서로 다른 작성 칸은 별도 항목으로 취급한다. 표는 열과 고정 행을 분석하고 셀별로 채운다.
3. **양식 속 예시 답안과 안내 문구는 사용자 사실이 아니다.** 원본 제목·표·페이지 구조는 최대한 유지하고, 작성 대상이 아닌 지시문을 결과 본문에 복사하지 않는다. 위치를 안정적으로 알 수 없는 영역에는 억지로 쓰지 않는다.
4. **사용자 사실과 AI의 문장 구체화를 구분한다.** 사용자가 준 아이디어의 목적·작동 방식·가치는 논리적으로 풀어 쓸 수 있다. 날짜, 기간, 사업비, 매출, 고객 수, 계약·투자·수상 실적, 경력처럼 제공되지 않은 사실은 만들어 넣지 않는다. 같은 설명을 여러 칸에 반복하지 않고 각 칸이 묻는 질문에 맞게 쓴다.
5. **정보 부족은 칸별 상태로 관리한다.** `ready`, `partial`, `missing`, `not_applicable`, `unsupported`, `non_input`을 구분한다. 보완 단계의 미입력과 사용자가 명시한 해당 사항 없음을 구별한다. 양식에 근거가 없는 칸은 공란으로 남기며, 임의의 `정보 부족` 문구를 양식에 채우지 않는다.
6. **PDF의 인쇄된 글머리표를 배치 기준으로 사용한다.** `○`, `-`에 맞춰 논점을 나누고 필요한 문장 수만 작성한다. 글머리표 자리에 긴 문장 조각을 억지로 끼워 넣거나 빈 글머리표를 채우려고 중복 문장을 만들지 않는다. 내용이 공간을 넘으면 출력 로직이 이어지는 페이지를 처리한다.
7. **프로필과 보완 입력의 출처를 구분한다.** 계획 정리에는 가입 프로필의 창업 상태·업종·지역을 빈 칸에 우선 채운다. 신청자 성명은 Backend가 로그인 사용자 정보에서 전달한다. 생년월일·성별·직업·기업명·기술분야처럼 현재 프로필에서 확보되지 않는 양식 항목은 계획 보완에서 묻는다.

## 4. 현재 구현과 계약

| 계층 | 관련 파일 | 현재 역할 |
| --- | --- | --- |
| Frontend | `Frontend/src/pages/BusinessPlanPage.jsx`, `Frontend/src/businessPlanSupplement.js` | 단계 전환, 공고 카드 검색, 양식 업로드, 보완 입력·페이지네이션, 초안 수정, 평가, 다운로드, 사용자별 브라우저 임시저장 |
| Backend | `Backend/api/bizplan.py`, `Backend/schemas/bizplan.py`, `Backend/services/bizplan_service.py` | 인증 API, 프로필 성명·공고 기준 전달, 요청 검증, LLM 문서 API 호출 |
| LLM | `LLM/src/rag/backend_tasks.py`, `LLM/src/serving/rag_routes.py`, `LLM/src/features/business_plan_documents.py` | 칸별 정보 분석, 초안·평가, PDF/HWPX 입력 위치 추출과 원본 양식 기반 출력 |

사용하는 Backend API는 `POST /bizplan/refine`, `/template-inspect`, `/generate`, `/evaluate`, `/render`이다. 현재 칸별 분석은 별도 응답 스키마가 아니라 `/generate`에 `__FIELD_ANALYSIS_V1__` 표시를 보내고, `sections[].content`에 분석 JSON을 담아 반환한다. 보완 정보도 `templateText`의 `__FIELD_CONTEXT_V1__` 표시로 전달한다. LLM 코드에는 장기적으로 분석 전용 타입 API가 필요하다는 TODO가 남아 있다.

PDF 양식을 넣으면 PDF로 출력하고, HWPX 양식은 HWPX 또는 PDF로 출력한다. 양식이 없으면 기본 양식을 사용한다. 계획 보완 이미지는 PNG/JPEG만 허용하며 파일당 2 MiB, 전체 4 MiB 제한이 있다. 브라우저 임시저장에는 양식 데이터와 보완 답변·이미지도 포함한다. 저장 공간이 부족하면 사용자에게 실패를 알린다.

## 5. 확인된 한계와 다음 검증

- **양식 인식은 범용성을 계속 검증해야 한다.** 현재 파서는 PDF 텍스트 필드 또는 추론 가능한 정적 입력 위치, HWPX의 표시·빈 문단·빈 표 셀을 대상으로 한다. 스캔 PDF나 입력 위치를 안정적으로 찾을 수 없는 파일은 거절할 수 있다. 특정 예시 PDF에만 맞춘 동작으로 성공을 판단하면 안 된다.
- **실제 파일 품질은 별도 확인이 필요하다.** 서로 다른 PDF/HWPX에서 본문과 표 구분, 글머리표 줄바꿈, 안내문 제거, 인적 사항, 이미지, 빈 셀, 여러 페이지 출력 및 원본 배치 유지 여부를 출력 파일로 확인해야 한다. 이 보고서 작성 과정에서는 새 파일별 시각 검증을 실행하지 않았다.
- **현재 초안 미리보기는 없다.** 사용자가 흐름상 제거하기로 한 최신 결정이다. 다운로드된 문서의 페이지 넘김 기능을 화면에서 검증하는 단계도 현재 제공하지 않는다.
- **분석 API는 기존 계약을 이용한 임시 구조다.** 장기적으로 `field_id`, 유형, 필수 정보, 상태, 누락 사유를 직접 담는 Backend 분석 응답을 마련하면 표시 문자열과 JSON 포장에 대한 의존을 줄일 수 있다. 이번 보고서에서는 코드를 변경하지 않았다.

## 6. 이번 보고서의 확인 범위

세션 요청과 첨부된 최신 요구사항을 현재 코드의 단계 목록, 생성·평가·출력 호출, 보완 상태 관리, PDF/HWPX 검사·출력 경로와 대조했다. 이는 현재 구현을 설명하는 문서이며, 새 양식에 대한 전체 기능 통과를 보증하는 테스트 결과는 아니다.
