# 검색 고도화 작업 흐름 보고서

작성일: 2026-10-02 · 범위: 정책·세금 검색 백엔드 고도화와 운영 선택

**기본 BM25 → Elasticsearch Nori 도입·튜닝 → 구형 평가 개선 확인 → 데이터·평가셋 확대 → 추가 실험과 재비교 → 기본 BM25 운영, Elasticsearch 보존**

한국어 형태소 분석을 활용해 검색을 개선하고자 Elasticsearch를 도입했다. 구형 데이터에서는 개선을 관측했지만, 근거 데이터가 추가된 뒤 새 평가셋으로 비교하자 그 우위가 유지되지 않았다. 최종 비교에서는 정책 적중률이 같았고 순위 지표와 세금 자동검사는 기본 BM25가 높았다. 운영 검색은 이 결과를 반영해 기본 BM25로 전환하고, Elasticsearch는 향후 데이터 변화에 따른 재평가를 위해 남겼다.

## 1. 출발점: 기본 BM25를 한국어 검색에 맞게 고도화

기본 검색은 어절과 문자 bigram으로 BM25 점수를 계산했다. 이를 한국어 형태소 분석을 사용하는 Elasticsearch Nori BM25로 확장했다. PostgreSQL Dense 검색, RRF 결합, Cohere 재정렬은 함께 사용했다.

처음부터 Elasticsearch가 더 좋은 결과를 낸 것은 아니다. 초기 Nori 검색이 기본 검색보다 낮게 나와 후보 구성과 검색 조건을 단계적으로 정리했다.

| 작업 | 바꾼 내용 | 목적·판단 |
| --- | --- | --- |
| 한국어 형태소 분석 | Nori tokenizer와 `decompound_mode=mixed` 도입 | 한국어 단어와 복합어를 형태소 단위로 검색 |
| 후보 단위 통일 | Dense는 정책별 최고 점수 청크, ES는 `policy_id` collapse 사용. RRF도 동일 정책의 중복 청크를 한 번만 반영 | 같은 정책의 여러 청크가 후보 자리를 소모하는 문제 완화 |
| 제목·본문 검색 조정 | `cross_fields` 적용, `minimum_should_match` 10~50% 탐색 후 25% 선택 | 제목과 본문에 나뉜 검색어를 함께 고려하고 최소 일치 조건 조정 |
| 품사 필터 조정 | 검색 analyzer의 stoptags로 조사·어미·기호를 제거하고 `XSV`·`XSA` 추가 | 검색어의 보조 표현을 줄이면서 핵심 의미 유지 |
| 후보 풀 조정 | Dense·Nori 검색 pool을 20/30/40/50으로 비교한 뒤 40 선택. RRF·Cohere 후보는 20 유지 | 정답 후보 확보를 늘리되 추가 이득이 없는 확대는 중단 |

부정·범위·법적 조건의 의미를 보존하기 위해 `VX`, `VCN`, `MAG`, `MM`, `XPN`, `XSN` 등을 공격적으로 제거하지 않았다. 사용자 사전은 사용하지 않았다. stoptag 변경만의 단독 효과가 좋아졌다고 주장할 수는 없으며, 후보 구성·Query DSL·후보 풀을 함께 개선한 흐름이다.

근거: [초기 Nori 고도화 상세 보고서](nori_retrieval_improvement_final_report.md), [9월 작업 기록](../../../LLM/work_log/WORK_LOG_0920_NORI_RETRIEVAL_HANDOFF.md).

## 2. 구형 데이터·평가에서 개선 확인

당시 작업 기록의 원본 문서는 10,892건이었다. 검색 단계 평가와 운영 응답 평가에서 다음 결과를 관측했다.

| 평가 | 측정 위치 | 기본·기존 기준 | 개선 Elasticsearch |
| --- | --- | ---: | ---: |
| 9월 개발용 정책 63문항 | Cohere 이후 검색 Top-5 | Hit@5 54/63 (85.7%) | 57/63 (90.5%) |
| 9/21 정책 63문항 비교 | 운영 응답 평가 보고서의 정책 Hit@5 | 53/63 (84.1%) | 58/63 (92.1%) |
| 9/21 세금 법령 18턴 비교 | 답변 자동검사 통과 | 13/18 (72.2%) | 14/18 (77.8%) |

이 결과로 Elasticsearch Nori가 한국어 검색 고도화의 유효한 후보임을 확인했다. 이후 서비스 검색·준비 상태·재색인 경로도 연결·보완했다.

**해석 범위:** 개발용 정책 63문항은 튜닝 과정에서 반복 사용했다. 9/21 운영 비교의 기본 기준은 9/16 결과를 재사용한 값이다. 따라서 위 수치는 당시 개선 흐름을 보여주지만 독립적인 미사용 평가셋에서 단일 변경의 효과를 증명한 결과는 아니다. 검색 Top-5와 최종 응답 지표도 측정 위치가 다르다.

근거: [구형 운영 비교 보고서](ELASTICSEARCH_COMPARISON_REPORT.md), [서빙·재색인 연결 기록](../ELASTICSEARCH_SERVING_CONSISTENCY_FIX_REPORT_20260922.md).

## 3. 데이터 추가 후 새 평가셋에서 우위가 바뀜

근거 데이터가 추가된 뒤 원본 문서 14,550건을 대상으로 신규 `holdout_cases_250.py`를 만들었다. 새 문항은 추가된 근거까지 포함해 작성했으므로 구형 평가와 질문·정답 문서 구성이 다르다.

| 영역 | 평가 단위 | 질문 예시 |
| --- | ---: | --- |
| 정책 검색 | 허용 질문 63건 | 서울 IT 개인사업자의 투자자 미팅 지원, 사업자 조건에 맞는 기술 진단·컨설팅 |
| 가드레일 | 차단 대상 63건 | 허용 범위 밖 요청의 차단 여부 |
| 세금 | 31개 시나리오 × 2턴 = 62턴 | 귀속연도 확인 후 세액 계산, 매입세액·공제·가산세를 반영한 부가가치세 계산 |
| 로드맵 | 31개 시나리오 × 2턴 = 62턴 | 사업 상황을 반영한 단계별 대화 흐름 |
| 합계 | 250개 평가 단위 | 정책·가드레일 문항과 세금·로드맵 대화 턴 |

새 평가에서 Elasticsearch의 정책 최종 인용 Hit@5가 52/63(82.5%)로 나와 기본 BM25와 비교를 시작했다. 후보를 40개로 늘린 Elasticsearch 결과와 10/1 16:20 기본 BM25 실행을 비교했을 때, 같은 후보 수의 정책 지표는 아래와 같았다.

| 신규 정책 평가·후보 40개 | 기본 BM25 | Elasticsearch |
| --- | ---: | ---: |
| 최종 인용 Hit@5 | 54/63 (85.7%) | 54/63 (85.7%) |
| MRR | **0.812** | 0.787 |
| MAP@5 | **0.743** | 0.713 |

Hit@5는 같았고 순위 지표는 기본 BM25가 높았다. 다만 이 초기 비교는 완료된 Elasticsearch 결과를 재사용했고 세금의 후보 수도 달랐다. 따라서 이후에는 양쪽 조건을 맞춘 전체 비교를 추가했다.

구형 평가의 92.1%와 신규 평가의 수치를 직접 빼서 데이터 추가에 따른 하락 폭으로 계산할 수는 없다. **새 평가셋 안에서 기본 BM25 기준선을 확보하고 같은 조건으로 비교해야 한다**는 점이 후속 실험의 출발점이 됐다.

## 4. 원인을 나눠 확인하고 추가 고도화 실험

단순히 검색엔진을 바꾸는 데서 끝내지 않고, 정답이 어느 단계에서 사라지는지 확인했다. 일부 문항은 검색 후보에 정답이 있었지만 RRF 상위 20개 절단에서 빠졌다. 요청 문구가 남은 검색어와 원문·개인화 검색 목록의 반복 기여도도 조사했다.

아래 정책 전용 실험은 **최종 답변을 생성하지 않고 Cohere 이후 입력 Top-5를 측정**했다. 최종 인용 Hit@5와 구분해야 하며, 같은 평가 문항을 보면서 탐색한 결과이므로 일반화 성능을 보장하지 않는다.

| 시도 | 관측 결과 | 적용 판단 |
| --- | --- | --- |
| RRF·Cohere 후보 20 → 40 | 별도 최종 응답 평가에서 정책 Hit@5 52/63 → 54/63. 개선 폭과 응답 시간 증가를 함께 검토 | 후보는 20으로 복원. 검색 pool 40은 유지 |
| RRF에서 Elasticsearch 기여도 1.3 적용 | 답변 전 Top-5 52/63 → 50/63. 1건을 살렸지만 Dense에만 있던 정답 3건을 잃음 | 기본 기여도 1.0 유지 |
| Regex로 요청 문구 정리 | 답변 전 Top-5 52/63 → 56/63 | 성능 상승은 있었지만 다양한 사용자 표현을 하드코딩해야 하므로 제거 |
| 복합 요구를 별도 LLM으로 분리 | 답변 전 Top-5 56/63 → 53/63. 처리 시간도 2.22초 → 5.46초 | 롤백 |
| 백엔드별 최상위 순위로 RRF 기여도 계산 | 요청 문구 정리 조건에서 답변 전 Top-5 56/63 → 57/63 | 유지. 같은 백엔드의 여러 검색어에서 동일 정책이 나오면 최상위 순위만 반영 |
| Nori 품사별 점수 가중치 | 2.5/0.5 조건의 전체 비교에서 정책 최종 인용은 기본 BM25 53/63, ES 50/63. 완화한 1.5/1.0 조건의 답변 전 Top-5는 52/63 | 개선 근거가 부족해 가중치 기능 자체 제거 |
| 라우터에서 검색 질의 재작성 | 기존 분기 LLM 호출이 검색 조건을 보존한 짧은 질의도 함께 생성하도록 변경 | 양쪽 검색기에 공통 적용. 중복 Regex 정규화 제거 |

라우터 재작성의 목표는 문장 요약보다 **검색 결과를 구분하는 조건 보존**이다. 지역·대상·업종·기간·수치·제외 조건을 남겨 초기 검색에 전달하고, Cohere 재정렬·근거 확인·최종 답변에는 사용자 원문을 유지한다.

이 단계에서 확인한 문제는 Elasticsearch 형태소 분석만의 문제가 아니었다. 후보 결합과 검색 질의도 결과에 영향을 줬다. 따라서 개선 효과가 확인된 공통 검색 흐름은 유지하고, 근거가 부족하거나 표현별 하드코딩을 요구한 실험은 되돌렸다.

## 5. 최종 공통 조건 비교와 운영 선택

추가 실험 뒤 10/1 22:40에는 양쪽 후보 수를 맞춰 전체 평가를 수행했다. 이후 라우터 질의 재작성과 중복 정규화 제거를 반영하며 재비교했다.

| 실행 | 당시 적용한 공통 흐름 | 기본 BM25 정책 Hit@5 | Elasticsearch 정책 Hit@5 |
| --- | --- | ---: | ---: |
| 10/1 22:40 | 요청 문구 정리·백엔드별 최상위 순위 RRF, 전체 250단위 | **59/63 (93.7%)** | 57/63 (90.5%) |
| 10/2 11:27 | 라우터 질의 재작성, 전체 250단위 | **55/63 (87.3%)** | 54/63 (85.7%) |
| 10/2 12:56 | 재작성 후 중복 Regex 제거, 정책·세금 재평가 | 56/63 (88.9%) | 56/63 (88.9%) |

각 행은 그 실행 안에서 조건을 맞춘 비교다. 행 사이에는 코드 조건이 달라졌으므로 시간순 성능 추세로 해석하지 않는다. [10/1 전체 비교](holdout250_bm25_vs_elasticsearch_20261001_224034_REPORT.md) · [10/2 전체 비교](../../../LLM/evaluation/results/holdout250_bm25_vs_elasticsearch_20261002_112748_REPORT.md).

라우터 질의 재작성과 중복 정규화 제거를 반영한 10/2 12:56 비교에서 정책 63건과 세금 62턴을 다시 실행했다. 양쪽 모두 원본 문서 14,550건, 같은 Dense 검색·프로필·프롬프트·gpt-6-luna, 검색 pool 40개, RRF·Cohere 후보 20개, 최종 Top-5를 사용했다. 세금 캐시는 OFF였으며 평가 프로세스는 운영과 분리하고 DB는 읽기 전용으로 연결했다.

| 최종 비교 지표 | 기본 BM25 | Elasticsearch | 판단 |
| --- | ---: | ---: | --- |
| 정책 최종 인용 Hit@5 | 56/63 (88.9%) | 56/63 (88.9%) | 동률 |
| 정책 Recall@5 | **80.2%** | 79.4% | 기본 BM25 소폭 우세 |
| 정책 MRR | **0.844** | 0.836 | 기본 BM25 소폭 우세 |
| 정책 MAP@5 | **0.766** | 0.750 | 기본 BM25 소폭 우세 |
| 세금 자동검사 턴 통과 | **46/62 (74.2%)** | 40/62 (64.5%) | 해당 실행에서는 기본 BM25 우세 |

Hit@5가 같다고 Elasticsearch가 미적용된 것은 아니다. 검증 기록에서 실제 백엔드가 구분됐고, RRF 후보 정답 포함은 기본 58/63·ES 57/63, Cohere 이후 Top-5는 57/63·56/63이었다. 마지막 인용 단계에서만 적중 문항 수가 같았다. 원본과 ES 색인의 문서 ID·내용 일치도 확인해 문서 누락을 원인으로 볼 근거는 확보되지 않았다.

정책 Hit@5는 최종 응답의 인용 정책 ID를 평가하므로 검색·재정렬·LLM 인용 선택을 함께 반영한다. 세금 통과율은 route/status/근거 등의 자동검사이며 정답 세법 문서 적중률이나 세액 정확도와 동일하지 않다. 가드레일·로드맵은 이 마지막 실행에서 재평가하지 않고 이전 결과를 재사용했다. 각 방식 1회 실행이므로 작은 차이에는 모델 응답 변동도 포함될 수 있다.

### 운영에는 기본 BM25 적용

최신 지표에서 Elasticsearch 우위가 재현되지 않아 운영 그래프의 키워드 검색을 기본 `BM25Search`로 변경했다. Dense 검색, 문서 단위 RRF, Cohere 재정렬, 라우터 질의 재작성은 유지한다. 공통 결합 클래스의 이름이 `NoriHybridSearch`여도 내부 키워드 검색 구현은 기본 BM25다.

### Elasticsearch는 후속 검증을 위해 보존

Nori analyzer, Query DSL, Elasticsearch 검색 구현과 재색인 코드는 남겼다. 데이터의 양과 종류, 사용자 질문 분포가 변하면 두 방식의 상대 성능도 달라질 수 있기 때문이다. 문서 증가만으로 ES가 더 좋아진다고 보장하지 않고, 새 데이터가 추가될 때 같은 조건으로 재비교해 운영 선택을 갱신한다.

현재 소스에 추가된 `NNB` stoptag는 마지막 비교의 live index에 반영되지 않았다는 제한도 있다. 후속 ES 평가에서는 의도한 analyzer 설정이 실제 색인에 적용됐는지 먼저 확인해야 한다. 품사별 가중치나 제거한 Regex 실험을 적용된 상태로 설명하지 않는다.
